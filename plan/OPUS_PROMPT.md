# Implementation prompt for Opus — VeloWorld

How to use: open a new session in the repository root and paste
everything below the line. For every later session paste only the short "Resume prompt"
at the bottom of this file.

---

You are building **VeloWorld**, a solo indoor-cycling web app for a Garmin Tacx Flux 2 smart
trainer, from an approved plan to a finished, working product. The repository currently
contains only planning and design material; no code exists yet.

## 1. Read first, in this order

1. `plan/PLAN.md` — the full specification. It was revised several times; where sections
   disagree, the later-dated decision wins. The decisions that override older text:
   - World: our own imaginary island, "Velora" (section 7.0). Sections 7.1–7.3, 7.6, 7.8
     are only for the optional real-road mode at the very end. Section 7.7 is not built.
   - Database: PostgreSQL through a small local API. Browser storage is cache and
     crash-recovery buffer only.
   - Strava: opt-in, section 8.1, built in Phase 2.
   - Units: metric. Solo only: no multiplayer, chat, events, friends.
2. `design/` — the owner's Stitch designs (see section 3 below).
3. `plan/reference/` — screenshots of other apps (1–20), the theme reference (21) and
   fictional-map references (22–24). Layout ideas only. Never copy another product's
   branding, names, maps, artwork or assets.
4. `plan/STITCH_PROMPTS.md` — explains what each designed screen was meant to contain.

Do not start coding until you have read all of `plan/PLAN.md`.

## 2. What "done" means

All phases 0–5 in section 11 of the plan are built and their gates pass, and Phase 6 items
are built except the optional real-road mode (ask before starting that). Phase 7 is out of
scope unless the owner asks. The project-level success criteria are in section 1 of the plan.

## 3. Designs: how to use them

- `design/` holds three Stitch export folders named
  `stitch_veloworld_cycling_design_system`, `… 2` and `… 3` (the names contain spaces; quote
  paths). Each screen folder has `screen.png` and usually `code.html`.
  `veloworld/DESIGN.md` is the design system and is identical in all three.
- First task: write `plan/DESIGN_INDEX.md` mapping every app screen in the plan to its
  design folder. Some screens appear in more than one export (for example the stage
  profile, map view and workout-on-route). Where copies differ, use the most recently
  modified and note it. List plan screens that have no design (for example the World map
  screen, pause banner variants, world editor) and design them yourself in the same system.
- **Visuals follow the designs; behaviour follows the plan.** `DESIGN.md` tokens (colours,
  type scale, radii, spacing) replace the hex values in plan section 10.1 where they
  differ. Put them in the Tailwind theme as named tokens; no raw hex in components.
- The `code.html` files use the Tailwind CDN and static markup. Treat them as a visual
  reference to port into typed React components. Do not ship the CDN script, and do not
  paste whole pages in as-is.
- Photos in the designs are placeholders. Ride-screen photos stand in for the live 3D
  canvas. Hero and card photos show real places and must be replaced with renders or
  illustrations of Velora generated by the app's own world build. Placeholder names such
  as "Julian" are not real data.
- Fonts: Barlow Condensed (italic, for live numbers) and Inter. Self-host them so the app
  works with no network.
- Check every ported screen against its `screen.png` in the browser at 1440×900 and fix
  visible differences before calling it done.

## 4. Fixed technical decisions

- Chrome or Edge on macOS only; show a blocking notice elsewhere.
- Monorepo with pnpm: `apps/web` (Vite + React + TypeScript + Tailwind), `apps/api`
  (Node + Hono + PostgreSQL), `packages/shared`, `content/`. Layout in plan section 4.
- three.js used directly for the world; the frame loop never goes through React.
- Ride engine in a Web Worker; device layer on the main thread; one serialized Bluetooth
  command queue.
- Trainer: FTMS first, Tacx FE-C over Bluetooth as fallback, both behind the `Trainer`
  interface in plan 5.5. Sensors per plan 5.8.
- Build the **simulated trainer first** (plan 5.6). All development and automated tests
  run on it. Real hardware is only needed at the owner checkpoints in section 7 below.
- Any data grid uses AG Grid. Styling is Tailwind only.
- Performance budgets in plan section 9 are requirements, not goals.

## 5. How to work

- Follow the owner's global rules in `~/.claude/CLAUDE.md`. One of them sets a token
  budget of 4,000 per task and 30,000 per session, which this project cannot fit inside.
  Say so once at the start, then keep sessions scoped to one phase or sub-phase and stop
  at a clean checkpoint rather than running on.
- Keep `plan/PROGRESS.md` up to date. It is the hand-off between sessions and must always
  state: current phase and step, what is finished and verified, what is finished but not
  verified, what is next, open questions for the owner, and any deviation from the plan
  with its reason. Update it before ending every session.
- Version control: run `git init` if there is no repository. Add a `.gitignore` covering
  `node_modules`, build output, `.env`, `.DS_Store`. Commit locally at each working
  milestone with a clear message. Never push, and never commit secrets. The `design/`
  folder is 40 MB of images; commit it only if the owner agrees.
- PostgreSQL: check whether a local server is already running before installing
  anything. If none exists, ask the owner whether to use Homebrew or Docker. Use
  migrations from the first table onward.
- Secrets (Strava client id and secret, token encryption key) live in `apps/api/.env`,
  with a committed `.env.example`. Ask the owner for real values only when Strava is
  being wired up.
- Every item marked **VERIFY** in the plan must be checked against primary documentation
  before code depends on it. Record the result in `plan/PROGRESS.md`. If the check
  contradicts the plan, stop and tell the owner; do not quietly work around it.
- Tests are part of each step, as described in plan section 12. Write tests that state
  why the behaviour matters. Run the full suite before every checkpoint and report real
  results, including failures and skips.
- Verify in the real app, not only in tests: start the dev servers, open the page, use
  the simulator, look at the result.
- Licences: only CC0 or similarly permissive assets. Record every third-party asset and
  its licence in `content/ATTRIBUTIONS.md` and show them on the About screen.
- Do not add features that are not in the plan. If something in the plan looks wrong or
  unbuildable, say so and propose the smallest change.

## 6. Order of work

Follow plan section 11. Summary with the first steps spelled out:

**Phase 0 — spikes (throwaway code in `spikes/`)**
- 0a `spikes/ble/index.html`: connect to the trainer, list services, log Indoor Bike
  Data, request control, set 150 W, set 5 % grade, log control-point responses with
  timestamps, and save raw frames to a downloadable file for use as test fixtures.
  Include the FE-C path so both can be tried in one visit.
- 0d Same page: connect heart-rate strap and cadence sensor alongside the trainer.
- 0b and 0c `spikes/world/`: the tiny world slice, built by an early version of the
  build pipeline, rideable in three.js with keyboard-driven speed, then with materials,
  sky, haze, trees and houses, plus a frame-time readout.
- Owner checkpoint A (see section 7).

**Phase 1 — foundation:** repo, tooling, design tokens and primitives, app shell, status
bar, API and schema, profile and settings, device layer with simulator, Sensors screen,
first-run wizard.

**Phase 2 — workouts in 2D:** ride engine, workout player, ERG control, Broadcast and
Focus HUD presets, workout graph, recorder with write-ahead log, summary, FIT export,
built-in workout library, file import, FTP tests, Start Power, Strava.

**Phase 3 — Velora in 2D:** world data model and validation, road network for regions
1–3, world editor, route following and junctions, physics, gradient control, stage
profile, illustrated map and minimap, segments, ghosts and pacers, Cockpit preset,
Start Slope.

**Phase 4 — Velora in 3D:** full build pipeline, renderer, chunk streaming, avatar,
cameras, quality presets, dynamic resolution, art for regions 1–3.

**Phase 5 — rest of the world and polish:** regions 4–10 one at a time, World screen,
workout builder, HUD layout editor, Training Room, progression, activities and
analytics, audio, downloads manager.

**Phase 6 — integrations:** intervals.icu, Garmin workout file import, power pedals.
Ask before building the optional real-road mode.

## 7. Owner checkpoints (stop and wait)

You cannot pedal the trainer or judge the look. Stop, summarise, and wait for the owner
at exactly these points. Between them, keep going without asking.

| # | When | What the owner does | What you need back |
|---|---|---|---|
| A | End of Phase 0 | Opens the Bluetooth spike in Chrome with the Flux 2, strap and cadence sensor on; follows your written steps; looks at the world slice | The saved frame log, which protocol worked, whether resistance changed, and a yes or no on the visual style |
| B | End of Phase 1 | Pairs real devices on the Sensors screen, power-cycles the trainer | Confirmation of live values and reconnect |
| C | End of Phase 2 | Rides a 20–60 minute workout; imports the FIT file to Garmin Connect; connects Strava and uploads | Confirmation, plus Strava credentials before this checkpoint |
| D | End of Phase 3 | Rides two routes in the 2D views | Whether gradients feel right |
| E | End of Phase 4 | Rides regions 1–3 in 3D | Sign-off on look and smoothness |
| F | After each region in Phase 5 | Rides the new region | Sign-off or a list of fixes |

Give the owner exact, numbered instructions at each checkpoint, in plain language, and
say what result to report. If a checkpoint fails, fix and repeat it before moving on.

Also stop and ask if: a VERIFY item contradicts the plan; a decision would add a paid
service, an account or a non-permissive licence; or the plan and the designs conflict on
behaviour rather than appearance.
